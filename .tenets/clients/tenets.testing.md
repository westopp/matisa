# Testing tenets — clients

Governance for how client applications in this repository are tested. Tenet IDs are stable; cite them in PR descriptions, code review, and CI output (e.g. "violates CTEST-200"). Numbers are identifiers, not priorities.

---

## CTEST-200. Every client ships a Lighthouse audit as a blocking e2e quality gate.

Every client application carries a Lighthouse audit, configured in a `lighthouserc.{js,cjs}` at the client root, that runs in CI on every PR and **blocks merge** when its budget assertions fail. The audit runs against the **production-mode** build (minified, prod env, served the way real users receive it) — never the dev build, never an in-process render. It runs in real headless Chrome (the lhci docker image is the sanctioned way to keep Chrome pinned; an unpinned runner drifts and produces apparent regressions that are tooling noise). It runs the **mobile preset with simulated network and CPU throttling** — the desktop preset hides regressions that real users hit on real phones. It runs **N ≥ 3 times per audited route and takes the median** — single-run Lighthouse scores swing ±5–10 points and produce false failures. Its `assertions` are configured at the blocking level, never `warn`-only — a non-blocking gate communicates that performance isn't a release criterion, and the build proceeds to ship the regression. The audited route list covers the user-facing surface a real user reaches in the first sixty seconds of use — the unauthenticated landing route, the primary authenticated entry point after sign-in, and any high-traffic flow in between; deep admin or settings pages are out of scope unless their performance is a product concern, and the list is declared in the lhci config. Auth-required routes are exercised by a Puppeteer hook that performs the sign-in flow before the audit; the hook lives next to the lhci config. The numeric budgets the gate asserts (LCP, TBT, CLS, transferred JS, total transfer weight) live in the lhci config — they are the measurement contract, not a tenet, because they describe a runtime outcome rather than a coding decision; the coding decisions that produce a good outcome are governed by [tenets.performance.md](./tenets.performance.md). A client without this gate, with a non-blocking gate, with a desktop-only gate, or with a single-run gate is not shippable under these tenets.
