# Analytics tenets

This file governs analytics-event emission — the producer-side discipline for what gets shipped to the analytics warehouse (currently BigQuery via the analytics module). Operational telemetry — traces, logs, metrics emitted through OTel — is owned by [tenets.telemetry.md](./tenets.telemetry.md); the dividing line between the two surfaces lives there as TEL-202.

Tenets are stable, prescriptive commitments. IDs are stable references — code review, PR descriptions, and incident postmortems can cite them. Numbers are not hierarchical; they are identifiers.

---

## ANA-200. Analytics emits success events; system failures route to telemetry.

An analytics event represents a *user or domain success* — a sign-up completed, a todo created, an invitation accepted. System failures (database errors, network blips, internal validation, bugs) belong to the operational pipeline (TEL-202) and are never emitted to the analytics warehouse: no `todo.create_failed` row when the database rejected a write, no `user.signup_errored` row when an exception bubbled, no analytics emission inside a generic error path. The on-call reads system failure in OTel; the analytics warehouse stays clean of noise it cannot aggregate into product insight. The carve-out is failures that are themselves *product signals* — user-state outcomes a product dashboard would query in a funnel: sign-up blocked because the email already exists, payment declined by the gateway, free-tier quota hit. These are emitted as analytics events with deliberately failure-shaped names because the funnel question warrants them. The discriminator is *user choice or state* versus *system fault*: the former earns analytics emission on a per-event deliberate decision, the latter never does. The bug class closed: analytics warehouses filling with operational error noise that doesn't aggregate into product insight, dashboards drifting toward error-rate panels duplicating Grafana, and the dividing line between "things that happened" and "things that broke" hollowing out.

## ANA-201. Event schemas are domain-owned and registry-declared.

Every event has a typed schema declared in its domain module's `<module>.events.ts` file. The analytics service receives typed payloads and ships them; it does not invent event shapes, mint event names at the call site, or accept arbitrary `{ name: string }` strings outside the registry. The registry is the answer to "what events does this app emit?" — reading the events files across modules enumerates the full surface, and code review can verify that every emission corresponds to a declared event. Cross-module consumers of event schemas import through the consumed module's index per ARCH-212. The bug class closed: ad-hoc emissions accumulate over releases, the warehouse fills with one-off event names no consumer maps, dashboards reference events nobody can find in code, and "is this event still emitted?" becomes a grep-and-hope question.

## ANA-202. Event names follow `noun.verb` past-tense, lowercase, dot-separated.

Event names are stable identifiers consumed by dashboards, queries, and downstream pipelines; their shape is fixed. The pattern is `<noun>.<verb>` in past tense, lowercase, dot-separated: `todo.created`, `org.member_invited`, `subscription.renewed`, `file.uploaded`. No camelCase (`todoCreated`), no spaces (`"Todo Created"`), no present tense (`todo.create`), no version suffixes (`todo.created.v2` — `event_version` is the column for that). Renames are breaking changes; the right migration is to add the new name, dual-emit while consumers move, then retire the old. The bug class closed: dashboards diverge as names drift across teams and time, the warehouse acquires three names for the same logical event, queries break silently when a name shifts in capitalisation or tense.

## ANA-203. Properties carry IDs and bounded aggregate values; PII is processed to extract structural signal, never emitted raw.

Raw PII — emails, phone numbers, names, addresses, free-text bodies — and arbitrary substrings of PII — first-letter-of-email, last-four-of-phone — never appear in analytics properties. Substrings preserve individual-level signal without adding aggregation value, and the analytics warehouse is the worst place to leave re-identification risk given its retention horizon and broad query access. *The corollary is not to drop the field.* Process the raw value at the emission site and emit the processed result: extract `email_domain`, `phone_country_code`, `signup_year_month`, address country, user-agent family — bounded, aggregation-meaningful slices that answer population-level questions like "what fraction of users are on `@acme.com` email?" or "which country codes dominate sign-up?" The discriminator at the emission site: does the value answer a population-level question, or is it a per-individual hint? Population-level extractions are encouraged — they're the entire reason analytics exists. Per-individual hints are not. Operational-log redactions (`redactEmail`/`redactPhone` outputs) belong in logs where line-level readability matters (TEL-214); they don't belong in analytics rows where the preserved characters add re-identification risk without adding aggregation value. The bug class runs both ways: timid teams emit empty fields because "PII == forbidden" and lose product insight that's available with one transform; bold teams emit raw or near-raw PII into a long-retention store because "we redacted it a little" and create GDPR and re-identification exposure. The rule is: process, then emit the processed thing.

## ANA-204. The subject is in the input; the actor comes from request scope.

The `userId` and `orgId` fields on a track input identify the *subject* of the event — the user or organisation the event is about. The *actor* (who triggered the request) is auto-derived from auth context and attached to logs and spans by middleware. In the common case the two collapse to the same identity; in admin-on-behalf-of cases (an admin updates another user's profile, a support agent acts on a tenant, a system process operates with elevated privileges) they diverge, and the analytics row captures the subject correctly even as the actor is something else. Callers do not pass the request-scope user as the input's `userId` for events whose subject is a different user — that's the silent miscategorisation this tenet exists to prevent. The bug class closed: admin actions attributed to the subject user in funnel analysis, support-driven changes counted as user behaviour, conversion metrics polluted by privileged-user activity that looks like ordinary user activity.

## ANA-205. Emission is single-point and service-owned.

A logical event is emitted exactly once per occurrence, by the service that owns the business outcome. Handlers do not emit — they translate transport into typed inputs, dispatch to services (ARCH-204), and the service decides what events its operation produces. Two services do not emit the same logical event for the same operation; if a coordinated action crosses service boundaries, one service is designated as the emitter — typically the one whose operation completing constitutes the event. The bug class closed: double-counting from emissions at both handler and service, dashboards diverging because the same event has two emission sites that drift apart over time, "where is `todo.created` emitted?" returning multiple results none of which are authoritative.

## ANA-206. Event versions bump on breaking property changes only.

`event_version` is incremented when an event's property shape changes in a way that consumers cannot transparently absorb: a property removed, a property renamed, a property's type changed, a property's semantic meaning altered. Adding a new optional property is non-breaking and does not bump. Old rows retain their original `event_version`; consumers that depend on shape filter by version. The migration for a breaking change is to bump the version literal in the event schema in the same diff as the property change, so the relationship is auditable in version control. The bug class closed: silent schema drift where a property's meaning shifts under consumers without warning, dashboard queries returning wrong shapes or missing fields after a release, and the inability to query "rows emitted before vs after the change" because nothing distinguishes them.

## ANA-207. Analytics emission is fire-and-forget; business logic does not depend on delivery.

`track`, `identify`, and `group` return the moment the buffer accepts; provider failures (BigQuery rejection, network blips, retry exhaustion, process crash before flush) do not propagate to business logic. No code path conditions on whether an event reached BigQuery — no waiting for an emission to complete before responding to the caller, no business outcome blocked on analytics state, no user-facing latency tied to streaming-insert latency. Validation errors are the one exception: a malformed event input returns `ServicePayloadError` because that's a programmer bug at the boundary, not an operational signal about delivery. The bug class closed: BigQuery outages affecting application latency or correctness, business flows that succeed in production but fail in test environments where analytics is mocked away, analytics quietly becoming a load-bearing dependency the operational architecture wasn't designed to support.

## Cross-references

- **TEL-202** — the dividing line between operational telemetry and analytics; ANA-200 is the producer-side rule on the analytics side of that line.
- **TEL-214** — PII discipline in logs; ANA-203 is the analytics-surface counterpart, tighter on substrings because of warehouse retention and access.
- **ARCH-204, ARCH-205** — handlers are thin, services own business logic; ANA-205 inherits this division for analytics emission.
- **ARCH-212** — cross-module imports go through the consumed module's index; ANA-201's registry surface follows the same rule.
- **SEC-205** — the actor (subject of authorisation) is read from the resolved session, not from the body; ANA-204 is the analytics-surface analogue for the subject of an event.
- **TEST-208** — service-tier tests assert behaviour, including that the right events are emitted for the right operations.
