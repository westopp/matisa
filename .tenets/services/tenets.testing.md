# Testing tenets — services

Governance for how services are tested. Tenet IDs are stable; refer to them in PR descriptions, code review, and CI output (e.g. "violates TEST-202"). IDs are identifiers, not priorities.

Cross-references:
- Module layout and file naming for non-test files live in [tenets.system-architecture.md](./tenets.system-architecture.md).
- Semtest background lives outside this repository: [overview blog post](https://medium.com/@thulane.dev/what-are-semtests-218db52ad9c8) and the full [semtest documentation](https://semtest.westopp.com). This file scopes semtests to their use inside the service tier.

---

## TEST-201. Four behavioural test tiers, mutually exclusive and sufficient.

Every test belongs to exactly one of four tiers — **unit**, **service**, **e2e**, **semtest** — and the four together cover everything in the system worth testing. The decision rule applies top-down, first match wins: a natural-language invariant evaluated by an LLM CLI is **semtest**; a test that crosses the wire (HTTP/RPC) against an externally running server is **e2e**; a test whose target is a service function is **service**; everything else is **unit**. Unit pins leaf logic — pure helpers, schemas, validators, parsers, formatters, anything *used by* services but not itself a service function. Service pins orchestrated behaviour on `ServiceShape` methods and is the centre of gravity of the suite (TEST-208). E2E covers the framework-shaped surface that only deployment shape can break — handler dispatch, transport, middleware ordering, real status codes, real auth flows, real serialisation. Semtests cover cross-cutting natural-language guarantees that no single line or function owns ("no service function leaks PII into logs", "every typed error has a matching error code constant", "every REST handler returns the standard response envelope"). No fifth tier — if a test does not fit one of the four, the test is the wrong shape, not the taxonomy. Out-of-scope quality gates (perf/load tests, type-level tests) have separate governance and are not tests under this taxonomy.

---

## TEST-202. Bucket by target, not mechanism.

The tier is determined by what code is under test, not by what is mocked or real. A test that exercises `TodosService.create` with a mocked `Database` Layer is a service test; the same function tested with `PostgresContainerLive` is also a service test; both live under `__tests__.<module>/`. No "unit test" label on a mocked-Layer service test because no I/O happens, no `unit/` vs `integration/` directory split based on whether containers are used, no separate CI gates for "unit service tests" and "integration service tests". Mechanism-based bucketing produces incoherent suites — the same service function ends up in two tiers depending on how the author felt that day, and "unit-test purity" arguments push real coverage into slow, brittle e2e tests instead of fast service tests.

---

## TEST-203. The service tier is not segmented by infrastructure.

Mocked-Layer service tests and real-container service tests (`PostgresContainerLive`, `LocalstackContainerLive` from `@repo/testing/containers`) live together in the service tier; required infrastructure is a prerequisite for the test, not a tier boundary. A `<module>.services.test.ts` file freely mixes `Database.TestLive` cases and `PostgresContainerLive` cases, choosing per-test based on what the assertion needs. No `<module>.services.unit.test.ts` / `<module>.services.integration.test.ts` split, no CI pipelines reporting "unit service tests" and "integration service tests" as separate gates. Splitting *files* for size or readability is fine (e.g. `<module>.services.create.test.ts`), provided the split is by behaviour or function — never by infrastructure. Both tests assert the same thing — a service function — and segmenting by infra fragments coverage, encourages duplication, and makes "what does this service actually do" hard to read off the suite.

---

## TEST-204. E2E is through-the-wire, against the actual application.

E2E tests live in `test/e2e/`, exercise the public REST/RPC surface, and assume the actual application is running with its real infrastructure (database, providers, telemetry collector). No importing `app` and calling its handler directly inside an e2e test, no node-level fetch mock to short-circuit the request, no starting the application inside `beforeAll`. The mechanism by which the application is started is a deployment concern, not a tenet concern — what matters is that the assertion exercises real handler dispatch, real serialisation, real auth, real headers, real status codes. Test setup may seed the database directly out-of-band before issuing through-the-wire requests; the *assertion* must still go through the wire. A test that boots the application in-process is a service test wearing an e2e hat, and its green result is false confidence in deployment-ordered behaviour the test never touched.

---

## TEST-205. Tests assert desired functionality, independent of implementation and outcome.

A test asserts what the system *should* do, derived from the requirement; it is not derived from what the current implementation does, nor adjusted based on what the test happens to produce when run. Implementation changes; the test stays the same as long as the desired functionality is the same. Test results may be red; the assertion stays the same as long as the desired functionality is the same. No backfilling assertions from running code — "the function returns 7, so I'll assert 7" is wrong; the assertion is what the function *should* return given the requirement, and if the requirement is unclear, the requirement is clarified first, never inferred from the code. No weakening or skipping a failing test to make the suite green — if the test correctly captures desired functionality, the failure is a real defect to fix in the production code; if the test does not, the desired functionality is re-specified explicitly (in conversation, in a ticket, in a doc), and only then does the assertion change, with a commit message that documents the new specification. No change-detector tests (`expect(result).toEqual(<paste of the function body>)`) — they break on every implementation change whether or not behaviour changed, and they happily assert any implementation bug they introduce. The test exists to specify behaviour; the implementation, the test runner, and the suite results are all downstream of the specification, and none of them feed back into it.

---

## TEST-208. Coverage is holistic and behavioural.

There is no numeric coverage target — numeric targets reward tests that touch lines without asserting behaviour and punish small modules already fully covered. Coverage in this codebase is *holistic and behavioural* (every test asserts something the system promises) and is binding by tier. **Unit:** for every pure helper, schema, validator, parser, or formatter, tests cover the happy path (every input shape that should succeed produces the expected output), the negative path (every input shape that should fail produces the expected failure), edge cases (boundaries, empty / min / max / just-over / just-under, null and undefined where allowed, unicode and whitespace where strings, negative and zero where numeric, plus any other edge relevant to the unit's domain — "edge case" is intentionally open-ended), and input-format variants (coercions, optional vs required fields, alternative valid representations of the same logical input). **Service:** for every service function (a public method on `ServiceShape`), every output shape under valid inputs is asserted on the success channel, and every typed error in the function's error channel has at least one test that produces the path raising it (adding a new tagged error to a service function's channel requires adding the corresponding test in the same change), plus every input-validation failure (`ValidationError` from the boundary Schema) is exercised; the test asserts the return value of the service function — not the internals of dependent services (those are the dependent services' tests' responsibility), not observability emissions (Effect guarantees those, not us), not access-control decisions made outside the service layer, not that database transactions work (the database service's own concern). **E2E:** for every endpoint in the API contract, every documented response (happy-path, error, status code) is exercised, every response is parsed through its API contract schema (`RestApiSuccessResponseSchema(...)` / `RestApiResponseErrorSchema(...)`) and the test fails on any divergence, list endpoints exercise pagination, filtering, and sorting, and endpoints are tested against malformed JSON, oversized payloads, injection-style strings, missing required fields, and type-mismatched fields — failing **consistently** (the same class of abuse always produces the same response) and **gracefully** (no 500s, no leaked stack traces, no unhandled exceptions on the wire). Out of scope here: middleware behaviour (TEST-216), observability pipeline health (TEST-217), and database transaction primitives (the database service's own surface).

## TEST-209. Tests own their seed data; the test environment is freely mutable.

Each module's seed fixtures live in a companion `__seeds__.<module>/<module>.seeds.ts` directory alongside the module source; test files import from the seeds module, do not inline large fixture literals, and do not share a global fixture store. Cross-module e2e tests in `test/e2e/` may reuse seeds from multiple modules; the import direction is `e2e → module seeds`, never the reverse. No repo-wide `test/fixtures/` directory shared across modules, no fifty-line fixture literals inlined in test bodies, no shared seed object mutated across cases. Tests may freely mutate the test environment — drop tables, truncate rows, reset sequences, reseed from scratch between cases — but **before any destructive operation, the test (or its setup helper) must verify that the running environment is the test environment** (asserting `NODE_ENV === "testing"`, `TEST_ENV`, or an equivalent guard). A `beforeEach` that runs `db.execute(sql`TRUNCATE …`)` without first asserting the environment is a production incident waiting to happen. Co-located, per-module seeds keep tests legible (the fixture's shape is one click away), keep tests independent (no global mutable seed state), and keep refactors local; separating `__seeds__.<module>/` from `__tests__.<module>/` keeps fixture builders re-usable by both unit and service tests without a circular directory dependency. The seed mechanism itself is expected to evolve — when it does, update the exemplar; the tenet stays.

---

## TEST-210. Semtests cover what unit, service, and e2e tests cannot.

Semtests assert pattern-shaped, cross-cutting, or natural-language guarantees that conventional equality and exception-tag checks cannot express — a security guarantee ("no service function leaks PII into logs"), a contract guarantee ("every typed error has a matching error code constant"), a structural guarantee ("every REST handler returns the standard response envelope"). The LLM evaluates the assertion because the assertion itself is semantic, not because we wanted a softer alternative to deterministic testing. Semtests are authored from human intuition about the system's semantic risks; an LLM does not decide what semtests to write. A semtest that re-asserts behaviour any unit, service, or e2e test could already make is a misplaced test — converted to the appropriate tier or deleted, never preserved as a parallel softer assertion of behaviour we already cover deterministically.

---

## TEST-211. Test file location and naming conventions.

Tests are co-located with the module they cover. Unit, service, and semtest files live in the module's `__tests__.<module>/` directory; e2e tests live in `test/e2e/` because they target the deployed surface as a whole, not a module. Filenames follow a fixed scheme so the suite is grep-able and the tier of a test is visible from its filename: unit is `<module>.<facet>.test.ts` (e.g. `todos.schemas.test.ts`); service is `<module>.services.test.ts` (or split by function: `<module>.services.<fn>.test.ts`); e2e is `<module>.<protocol>.e2e.test.ts` (e.g. `todos.rest.e2e.test.ts`); semtest is `<module>.<invariant>.test.md`. Within a test file, `describe` blocks name the unit under test; `it` / `test` blocks state the behaviour as "returns X when Y" or "fails with Z when Y". No `<module>.test.ts` (no facet — ambiguous tier), no `it("works", …)`, no `describe("misc", …)`, no `<module>.integration.test.ts` (segments by infra; see TEST-203), no top-level `tests/` mirror tree, no tests for module A living inside module B's `__tests__.b/`. Predictable filenames mean any contributor can locate a test by grep and infer its tier from its name; behavioural test descriptions read as a specification of the system.

## TEST-213. Do not test what we already trust.

Tests assert behaviour our team owns; we do not write tests for third-party libraries, language primitives, or framework features that come from reputable sources and are exercised by their own test suites. If Effect's logger, Drizzle's query builder, or Bun's `fetch` is broken, the failure surfaces somewhere we own, and the fix is upstream — not in our suite. No test named `"effect logger writes structured logs"`, no test re-asserting that `Effect.gen` short-circuits on the first failed step, no test verifying that `postgres-js` parameterises queries; instead, a service test asserts "TodosService.create persists a row and emits the expected span", and a unit test asserts our schema's rejection rules — not Effect Schema's general parsing behaviour. A wrapper we author over a third-party library is tested only when it adds custom code we own (validation, transformation, error mapping, behavioural choices); a thin wrapper that contains no custom logic — pure forwarding, type re-exports, configuration plumbing — does not need its own test, because there is nothing of ours to assert beyond what the underlying library or its own tests already cover, and a wrapper over already-tested code (our own utility module, an internal package with its own coverage) does not need duplicate coverage at the wrapper boundary. Re-testing trusted dependencies wastes maintenance effort, makes the suite larger and slower without adding signal, and creates the illusion that we own correctness we do not.

---

## TEST-214. Quality of guarantee beats speed of execution.

Choosing between a fast test that asserts a weaker guarantee and a slower test that asserts the real one, we choose the real one. For the **service** tier specifically, prefer real test infrastructure (Testcontainers Postgres, Localstack, provider sandboxes) over mocked Layers whenever the real dependency is reachable in CI and on a developer machine; for **e2e**, real infrastructure is mandatory by definition (TEST-204). A test that runs in 50ms but asserts only what we already know from types adds little; a test that runs in two seconds but exercises the actual database — its FKs, indices, error codes, transaction semantics — produces a guarantee that survives contact with production. Speed is a real constraint, but it is secondary to whether the test catches the bugs we ship.

---

## TEST-215. Every test asserts a real-world utility guarantee.

Every test must, in one sentence, state what guarantee it provides about the running system; if a test cannot answer "what real-world failure does this prevent, or what meaningful aspect of this system does it assert?", it does not earn its place in the suite. The asserted aspect must be valuable to either the **integrity of the running system** (correctness, security, data consistency, observability promises) or the **experience of any of its users** (developers integrating with the API, end-users hitting handlers, operators reading logs). Tests are not coverage decoration — they are insurance against specific, articulable failure modes in production. Tests written to satisfy review, hit a number, or document API shape produce noise without signal; they grow the suite, slow the build, and dilute the meaning of green CI. A service test's `it` description reads as a valuable guarantee, and every test earns its place.

---

## TEST-216. Middleware has its own dedicated test surface.

Middleware applies uniformly across endpoints, so asserting middleware behaviour inside every per-module e2e test produces churn without signal — change one middleware, update fifty test files. Middleware is therefore tested once in dedicated `middleware.<name>.test.ts` files (currently `middleware.rate-limit.test.ts`, `middleware.security-headers.test.ts`, `middleware.strip-stack-error.test.ts`, `middleware.validation-error.test.ts`), and per-module unit, service, and e2e tests do not reassert middleware-owned behaviour. Adding a new middleware to the stack adds a new `middleware.<name>.test.ts` file alongside these; removing or replacing a middleware removes or replaces the corresponding test file — the set of files is the visible inventory of the middleware stack. Beyond the dedicated tests, middleware behaviour is informally observable in the responses captured by e2e tests (status codes, headers, error envelopes); authors reviewing e2e output sanity-check that middleware-shaped responses look correct, but these manual observations are not codified as per-endpoint assertions.

---

## TEST-217. Observability pipeline health is verified by a manual smoke test.

The observability pipeline — application logs, traces, and metrics flowing through the OTel collector to the configured backends and surfaced in Grafana — is verified by a dedicated **manual, human-driven** smoke test: a human starts the application with its real telemetry infrastructure, exercises a representative slice of behaviour, and visually confirms in the dashboards that logs are searchable, traces connect end-to-end, and metric counters and histograms populate as expected. Not automated, by design — an automated pipeline test would assert that the pipeline produces output, not that the output is *useful*, and an observability stack that produces noise no one reads is functionally broken even when every assertion passes. A human reading the dashboards is the actual quality gate. We do not assert observability emissions per service function (TEST-208) — Effect emits the spans, logs, and metrics, and we trust Effect; the smoke test confirms the *pipeline transports them*, the *backends ingest them*, and the *dashboards render them usefully*, and that is the only assertion that matters.

---

## TEST-218. Tests are deterministic.

Tests must produce the same result every time given the same inputs and a clean test environment. Non-determinism is a defect, not a flake — a test that fails one run in fifty has correctly flagged a real bug fifty times less often than a test that fails reliably, and silenced it the other forty-nine. Each common source of non-determinism is a bug to fix at the source: **time** (wall-clock reads, `Date.now()`, `new Date()`, system timers — use a controllable clock such as Effect's `TestClock` or freeze the relevant time at the test boundary); **randomness** (unfixed RNG seeds, UUIDs generated inside the system under test — inject the source so the test fixes the seed); **concurrency** (assertions that depend on operation order across promises, fibres, or workers — either serialise the assertion or assert on the set of outcomes, not the sequence); **shared infrastructure** (port collisions, fixed file paths, container reuse across cases — each test gets exclusive access to its resources, or the resources are reset between cases); **order dependencies** (a test that passes only when run after another — the fix lives in the test that leaks state, not in the test that observes the leak). The response to a failing test is never `.skip`, a retry decorator, or a weakened assertion (TEST-205); the response is to find the source of non-determinism and remove it.

---

## TEST-219. Tests are isolated; one test's state does not affect another's.

Each test begins in a known initial state and ends with that state restored, so any test can run in any order, in parallel with any other, and produce the same outcome it would in isolation. **Within a file:** between cases, mutations to shared infrastructure (database rows, queue contents, filesystem state) are reverted via truncate-and-reseed, transaction rollback, or fixture reset; the mechanism is the test's responsibility, not the framework's, and a `beforeEach` that does not reset what the previous case mutated leaks state. **Across files and workers:** when the test runner uses parallel workers, shared infrastructure is partitioned (per-worker DB schemas, per-worker S3 prefixes, per-worker temp directories) or the conflicting tests are serialised; two tests in different files writing to the same row have a race, and the fix is partitioning, not coincidental ordering. A test that passes in isolation but fails when run with the rest of the suite has identified real cross-test contamination — investigate, find, and fix the leak; never reach for a retry decorator or a `--runInBand` workaround that pretends the contamination is not there. This tenet is the runtime counterpart to TEST-209 (structural ownership of test data) and TEST-218 (runtime determinism); together, the three say tests own their data, behave deterministically, and do not leak.
